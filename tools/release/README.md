# Source-side automatic Alpha signing

This is opt-in infrastructure for a dedicated trusted Linux release host, **not** an application feature or a public Render web service. It never generates a replacement signing key. The existing owner fingerprint DA269C59E903F28BD46DA217F88380E446488691 and binary public anchor pin remain unchanged.

## Trust boundaries and one-time provisioning

Use three separate service identities: trusted test orchestrator, validator, signer. Install a reviewed immutable copy of this source under root-owned /opt/syspulse-release. Do not give the signer access to untrusted build workspaces or execute candidate packages on that host. The orchestrator must produce the actual test attestation after a controlled build/upgrade run. Public reports, GitHub source writes and a catalogue entry alone never authorize signing. Keep orchestrator and validator handoff directories protected against writes by the signer and other users; the attestation/approval files may be readable by a dedicated release-readers group. Root and the dedicated producer must own all ancestors, with no group/world write.

Provision the original private key once, through a trusted host administrator's secure transfer procedure, into the signer-owned 0700 /var/lib/syspulse-signer/gnupg. Verify the fingerprint independently before activation. Protect encrypted backup and recovery access. Never paste the key, passphrase or Git credential into chat, commit them, expose them to a build service or send them through a public HTTP endpoint. Use a minimal repository-scoped Git HTTPS credential, branch protection as available, and host secret delivery. The supplied service templates use systemd LoadCredential from administrator-managed root-only files under /etc/syspulse-release/credentials. Test credential ownership/access and actual signing using the existing key in a staging transaction before enabling production. A passphrase-protected key needs loopback authorization and a correctly provisioned credential; an agent-based configuration requires a reviewed unit override. Do not remove the key passphrase to make this work. Configure the numeric VALIDATOR_UID in /etc/syspulse-release/signer.conf; provision the dedicated accounts/groups and protected state directories. A persistent signer state is mandatory.

## Automatic cycle

1. A controlled build orchestrator runs native regressions, exact signed prior-DEB installation/upgrade, tamper rejection, runtime and package verification. It produces a protected attestation only after success. Register the exact immutable candidate digest and commit in release-candidates, never updates-alpha.
2. Invoke validator_handoff.py as the separate validator with --attestation /var/lib/syspulse-orchestrator/attestation.json --orchestrator-uid NUMERIC_UID --output /var/lib/syspulse-validator/approval.json. It independently verifies the current signed feed, catalogue match, expiry, artifact digest, package identity and embedded owner public anchor before producing the protected approval. The orchestrator is a trusted component; this script does not itself run the native test suite or authenticate arbitrary public build logs. Do not wire untrusted build processes directly to the attestation path.
3. Run source_signer.py verify --state /var/lib/syspulse-signer as the signer. Run publish with --approval and --validator-uid but **without** --apply for a no-sign/no-push dry run. Only after validation and secure credential provisioning install and enable the provided systemd timers. Hourly publication checks and daily conditional metadata renewal are independent from the user's desktop. The signer never executes candidate scripts. It rechecks the current package hash, signature, approved origin, report, DEB digest, version and embedded trust pin. It signs both Release forms and verifies both locally and remotely. Existing approved version is a no-op. It never force-pushes.
4. If a push is uncertain, the journal blocks another push. Verify the signed remote and manually reconcile on the host if it is not the exact expected commit. Never erase state or disable rollback checks simply to retry. Keep the signer host patched and monitor failures.

Attestation schema: {"schema":1,"candidate":<exact catalogue row>,"verified_at":"ISO-8601 UTC timestamp","expires_at":"ISO-8601 UTC timestamp within 24h of verification","native_regression":true,"signed_upgrade":true,"tamper_rejection":true,"runtime":true,"package_verified":true,"physical_acceptance":false}. Physical acceptance is separately recorded; this policy is Alpha-only and does not certify stable releases. Minimum native suites is 54. Initial rollback floor is the published Alpha.32 hash; subsequent verified versions are recorded persistently. Never reset state to bypass the floor.

## Status and limits

Dockerfile.test is a **no-secret** evaluation image. Its public endpoint contains only test evidence. It does not sign or publish anything. Actual remote key provisioning, trusted test-orchestrator wiring, systemd service activation and live end-to-end owner-key signing require a dedicated trusted host. No GitHub Actions, CircleCI, or paid service is required by this source implementation, but availability of a suitable free always-on host is not established. Do not put secrets in an ephemeral public evaluation service. No automatic package installation is performed on client systems.
