# DEB Release Fleet v2 — deployment and adoption contract

This evaluation branch contains a reusable signing engine for one single-package, flat APT feed per project/channel/architecture. It does not change any production update feed. Legacy SysPulse source_signer.py remains present for compatibility; do not enable its production timers before migration review. The v2 engine imports only common helper primitives from that file.

## Threat model

A compromised public candidate catalogue or artifact server cannot by itself authorize a new release. The independent trusted test orchestrator must supply an attestation, the validator separately verifies the package/feed and emits a protected approval, and the signer revalidates it before signing and again before pushing. This does not protect against compromise of root, the trusted orchestrator, the signing host, or the private key itself. A public build report is not a cryptographic test attestation. No untrusted build code may run with validator or signer credentials.

## Enroll a project

1. Preserve the existing project's trusted public key and verify its exact fingerprint and binary SHA-256 out of band. Never reuse SysPulse's key by default or generate a replacement without owner instruction. If no existing trusted key/feed exists, bootstrap is a distinct reviewed operation, not supported by this publisher.
2. Configure a root-owned policy JSON (schema 2, example in policies/) in /etc/deb-release. Separate each package, channel, architecture, Git feed branch, allowed artifact host, existing signed version/hash, expected embedded public key path and test threshold. Stable requires physical acceptance. Policy changes require reviewed state migration; never reset rollback state.
3. Ensure the existing application's updater supports the canonical flat feed (Release, InRelease, Release.gpg, Packages, pool/). Canonical new filenames are pool/PACKAGE_VERSION_ARCH.deb, preserving the existing SysPulse alpha naming exception. Debian versions with epochs are deliberately excluded for now. Package size limit 64 MiB; expanded data archive limit 64 MiB; subprocess file cap 128 MiB. Large package/repository fleets, multi-package indexes, private Git clones, Windows executables, distro-specific repositories and bootstrap signing need separate extensions and tests.
4. Create separate unprivileged orchestrator, validator, and signer identities for every trust scope. Root owns the source installation, policy, and ancestors of state directories. A signer owns only its mode-0700 leaf /var/lib/deb-release/PROJECT/CHANNEL/ARCH, with dedicated gnupg inside. Use separate credentials and dedicated accounts; don't share a privileged signing account or expose secrets to builds. Provision existing secret key securely on the dedicated trusted host once; no private keys in Git, chat, HTTP endpoints or cloud build arguments.
5. The trusted build controller tests the exact currently signed previous package version AND hash. It must record native regressions, actual signed upgrade, tamper rejection, runtime and package checks; a stable candidate also needs physical acceptance. It writes a protected independent schema-2 attestation. Populate release-candidates-v2.json only after real testing. Candidate fields: project, channel, package, architecture, version, source, deployment, artifact_url, sha256, size, prior_version, prior_sha256, suites, build_report_sha256, install_report_sha256. Report hashes are over raw downloaded bytes, not copied webpage text. Both report files must be adjacent to the candidate DEB. Attestation fields: schema=2, candidate=exact row, verified_at, expires_at (max 24h), native_regression, signed_upgrade, tamper_rejection, runtime, package_verified, physical_acceptance. Public catalogue is discovery only.
6. Run fleet_validator.py with --policy, --attestation, --orchestrator-uid, --signer-uid and --output. The protected output must be named approval.json under project/channel/architecture. Signer reads but cannot modify it.
7. Run fleet_signer.py verify with --policy and --state; then run publish with --approval and --validator-uid, WITHOUT --apply. This performs read-only remote validation and candidate preparation, while recording local verified high-water state. No signing or push occurs. Confirm the exact candidate and stage an owner-key signing transaction in a separate explicitly authorized non-production repository with distinct policy/credentials before enabling production.
8. The opt-in systemd templates support hourly publication and daily renewal on systemd with LoadCredential and %d support (Ubuntu 24.04 class host). Copy reviewed source to /opt/deb-release, install units root-owned, choose a short instance name (e.g. sp-alpha), create its debrel-INSTANCE account and group, set /etc/deb-release/INSTANCE.json plus INSTANCE.conf with STATE_PATH, GPG_HOME, APPROVAL_PATH, VALIDATOR_UID. Provision root-only credential sources under /etc/deb-release/credentials/INSTANCE/. Test actual credential ownership and access, service sandbox and GPG loopback/agent before enabling timers. For agent-only deployments use a reviewed unit override, not an empty passphrase or insecure key export. The templates are not activated or tested on a real systemd host yet.
9. Exact-head lease is an atomic compare-and-swap, not an unconditional force push. The code proves the proposed commit has exactly one parent, the verified current remote head, before using the lease. Repository branch protection must also forbid unauthorized history rewrites. A concurrent change rejects publication; a pending journal blocks any blind retry. Preserve the journal and checkpoint, investigate the remote signed feed, and reconcile under operator control if needed.

## Release gates

The new engine must not be installed fleet-wide solely because unit tests passed. Required per project: client updater compatibility, exact-current-version upgrade test, protected independent orchestrator integration, non-production owner-authorized sign/push/readback, rollback/renewal/recovery drill, host isolation/credential verification and physical acceptance as required. No GitHub Actions, CircleCI, paid hosting, replacement keys or production updates were used in this evaluation.

## Residual risk

Git and dpkg parsers are trusted system dependencies; keep them patched. Use host disk/CPU/memory quotas and network egress allowlists; per-process output limits are not total disk quotas. Dedicated persistent state is mandatory. DNS, TLS and root-owned policy are trusted. The exact-head lease can block on protected branches; do not relax protection to bypass it. Existing owner private key is not available in this environment. No actual private-key signing or production publication has been performed.
