# Mandatory XFCE distribution and update policy

Owner requirement: always deliver a real .deb for the established SysPulse Qt application on Linux Mint 22.3 XFCE amd64, capable of updating the entire installed application from the canonical repository (https://github.com/sudipdasin/SysPulse). Applies to every distributable preview, beta, release candidate and stable release. Source-only development checkpoints are not releases. No substitute X11 prototype, empty package, unsigned bootstrap or shell installer presented as the required deliverable.

## Distribution
- Build on a compatible target VM, use the native CMake/CPack configuration and derive actual dependencies. Package the application, required helpers, menu entry, icon, documentation and updater components. Preserve user preferences and existing features.
- Run the complete inherited and new native tests, real desktop startup and package install/upgrade/uninstall checks. Record exact source commit, target, Debian version, SHA-256 and evidence. Sign and publish immutable assets on the canonical release channel, with a verified direct DEB download. Do not label a development checkpoint as a completed release if any gate is missing.
- No GitHub Actions or CircleCI. No paid resources or stable release without owner approval.

## Full application updates
Preferred distribution design: a signed, dedicated APT repository synchronized with canonical release artifacts. Enroll an independently authenticated public signing key using scoped Signed-By trust; verify signed repository metadata and package hashes. Never use trusted=yes, apt-key, unauthenticated packages, arbitrary root shell, or a mutable URL as sufficient trust. Keep the private signing key outside source control and test keys out of production.

Existing Qt Settings/Software panel should show installed version, latest eligible version, channel, check result, release information and update status. Enable automatic update checks with a clear preference and disable control; actual installation uses the system package manager and explicit administrator authorization, or separately configured opt-in automatic installation through the operating system. Stable channel by default for stable installations; previews require an explicit preview channel. Never overwrite a dpkg-managed executable directly. Use the full signed package, reject unauthorized downgrade or channel crossing, handle failed/interrupted updates truthfully and preserve configuration. Provide a supported recovery path using trusted retained packages and documented limitations; never promise transactional rollback if unavailable.

An authenticated signed release-package workflow may be used as an alternative to APT repository hosting only if it provides equivalent trust, immutable staging, downgrade/replay protection and package-manager integration. Existing offline verifier/staging components are a foundation, not a live updater.

## Release gate
Verify actual published asset, trust enrollment, live version discovery, tamper rejection, update from the preceding installed release, settings preservation, denied/cancelled authentication and interruption recovery. Run this on the intended XFCE target, not only with mocks. Report real test results and unresolved blockers. Do not distribute a package as compliant until automatic checks and complete-package update path actually work.

## Alpha.22 updater implementation checkpoint
# Full-package signed updater (alpha.22 candidate)

Client Settings & help → Application updates: choose Stable, Beta or Alpha, check the selected signed APT repository, review version and release notes, approve install through PolicyKit. Fresh metadata is fetched in isolated APT state. No trust-on-first-use. Package is installed by APT with explicit authorization; the helper checks the candidate again, rejects downgrade/channel crossing and unrelated changes and verifies installed version. Automatic checking is opt-in; legacy cached preference does not enable network requests. No unattended install. Restart after installation. Cancellation after dpkg starts is not rollback.

## Activation — release operator
Canonical feed locations: https://raw.githubusercontent.com/sudipdasin/SysPulse/updates-alpha/ (likewise updates-beta and updates-stable). These branches are not provisioned yet. Publish a verified immutable DEB under canonical Releases and generate signed flat metadata with tools/build-apt-snapshot.py; it now accepts evaluation Debian revisions. Use an owner-controlled offline OpenPGP signing key, never the disposable build key. Publish only the public key and signed snapshot; keep the secret key offline. Publish the snapshot as an atomic commit to the matching dedicated branch; do not add CI workflows. Retain prior packages and publish immutable release metadata separately. The signed Release expires after seven days, so renew signed metadata before expiry. Key enrollment must independently verify the full fingerprint, then install the exported binary public key at /etc/syspulse/update-keys/alpha.gpg (root-owned, 0644, parent dirs root-owned and nonwritable by other users). Repeat separately for other channels. Do not enroll unverified keys.

No update URL or signing key is accepted from user input; no raw unsigned install, no global APT trust or changes to system source lists. If the feed is missing or expired or key not enrolled the client fails closed. Recovery is manual using an authenticated retained package; no transactional rollback promise. Owner key provisioning, canonical publication and physical Mint tests remain required. Disposable test fixture is never the production signing key.

## Package-managed trust
# Package-managed update authentication

The release operator supplies an independently verified binary public OpenPGP key and SHA-256 for each channel using CMake SYSPULSE_ALPHA_PUBLIC_KEY and SYSPULSE_ALPHA_KEY_SHA256 (likewise BETA and STABLE). The build validates the digest, rejects secret-key packets and malformed exports, checks exactly one public primary key with GnuPG, and installs only the public key and its digest in /usr/share/syspulse/update-keys. The installed DEB is the initial trust anchor; the public key and digest inherit its authentication. No first-network-use trust, no user-generated signing key, no client identifier, no credential or private key in the app.

On each update check/install, the helper automatically selects the packaged channel key, verifies root ownership, permissions and matching SHA-256, and uses it for signed APT metadata. Invalid or partial packaged keys fail closed even if a legacy administrator key exists. Only if both packaged files are absent does the prior administrator-enrolled key path remain available for migration. Automatic network checks on startup and every 30 minutes require explicit opt-in; installation still needs administrator approval. Alpha builds default to the alpha channel unless a saved channel exists.

Production prerequisites: authenticated initial DEB, owner-controlled offline signing key, signed published snapshot and canonical immutable release. No test signing key is included in evaluation packages. No production key is provisioned by this source change. The local digest does not authenticate an untrusted initial DEB; it detects local mismatch against the package-managed pin. Key rotation requires a trusted signed package carrying the next key before the old key is retired. Never accept a key merely because it came from the update server.

## Metadata renewal policy revision
New updater builds accept at most 30 days of signed Release validity (and always respect earlier signed expiry). New snapshots use 30 days. Existing Alpha.26 clients retain their seven-day cap until upgraded, so renew existing metadata within that cap during migration. Use the canonical flat suite / to avoid raw GitHub's /./ redirect; redirects remain disabled. Use a generated early APT_CONFIG to exclude host config fragments. No private key or passphrase stored in application or cloud. Automated local renewal may sign only with an available authorized GPG agent; otherwise notify the release owner for approval. No unattended-signing claim without a protected signing service.

Alpha.27 candidate implements canonical HTTPS flat feed and maximum 30-day validity. Do not activate longer server validity until the corrected client is available. Daily local renewal checks may attempt metadata-only signing via the existing authorized GPG agent; if locked they must request owner approval, never collect/store a password. Actual unattended signing not provisioned.
